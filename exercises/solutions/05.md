## 1. [measure]

The temporary array has `n * m * d` values: 1000 × 1000 × 32 = 32,000,000. At 8 bytes each that is 256 MB. The result adds 1000 × 1000 × 8 bytes, which is 8 MB. The sum is 264 MB.

```python
import tracemalloc

import numpy as np

from examples.ch05_broadcasting import dist_broadcast

A = np.random.default_rng(0).random((1000, 32))
tracemalloc.start()
dist_broadcast(A, A)
_, peak = tracemalloc.get_traced_memory()
tracemalloc.stop()
print("values in the temporary array:", 1000 * 1000 * 32)
print("expected MB:", (1000 * 1000 * 32 + 1000 * 1000) * 8 / 1e6)
print("measured peak MB:", round(peak / 1e6))
assert abs(peak / 1e6 - 264) < 26
```

```text
values in the temporary array: 32000000
expected MB: 264.0
measured peak MB: 264
```

## 2. [break]

At an offset of 1e8, the squared norms are about 3e16. The gap between neighbor `float64` values at 3e16 is 4. Each term of the subtraction `|a|² + |b|² − 2a·b` has a rounding error of about one gap. The squared distance is wrong by a few gaps, about 16. The square root of 16 is 4.

```python
import numpy as np

from examples.ch05_broadcasting import dist_dot, dist_loop

for offset in (1e4, 1e6, 1e8):
    P = np.random.default_rng(0).random((30, 3)) + offset
    err = np.abs(dist_dot(P, P) - dist_loop(P, P)).max()
    print(f"offset {offset:8.0e}  max error {err:.2e}")
assert err > 1.0
print("gap at 3e16:", np.spacing(3e16))
```

```text
offset    1e+04  max error 3.45e-04
offset    1e+06  max error 3.12e-02
offset    1e+08  max error 4.00e+00
gap at 3e16: 4.0
```

The points lie in a cube of side 1, so the true distances are at most 1.7. An error of 4 is larger than every true distance. Centering removes the problem, because it moves the cube to the origin before the subtraction.

## 3. [judge]

**Position.** Ship the dot version with centering. Process the 50,000 points in blocks. Test it against the broadcast version on a sample.

**What a good answer weighs.** The broadcast version needs 50 × 50,000 × 128 × 4 bytes, which is 1.28 GB in `float32`. The machine has 8 GB. One request fits, and a few at the same time fail. The dot version needs about the size of the result, which is 10 MB.

Precision is the open question. Centering with the mean of the 50,000 fixed points works if they do not change between calls. If both sets change, the mean of the 50 query points is a cheaper way to center. A fixed reference vector also works.

**Strongest objection.** The dot version in `float32` loses digits even after centering, if the points are spread over a large range. The answer is to measure the error that the service cares about. For example, measure whether the nearest neighbor is the same one. Do not measure the distance error.

**What overturns the position.** Compare with the broadcast version in `float64` on real data. Suppose the nearest neighbor changes for more than a small fraction of the queries. Then use `float64` for the cross term, or compute the final candidates exactly.
