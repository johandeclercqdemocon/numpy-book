## 1. [measure]

```python
import timeit

import numpy as np

from examples.ch06_ufuncs import ma_cumsum, ma_window

x = np.random.default_rng(0).random(100_000)
ratio = {}
for w in (10, 1000):
    t_window = min(timeit.repeat(lambda: ma_window(x, w), number=1, repeat=3))
    t_cumsum = min(timeit.repeat(lambda: ma_cumsum(x, w), number=1, repeat=3))
    ratio[w] = t_window / t_cumsum
assert ratio[1000] > 10
assert ratio[1000] > ratio[10]
print("window time grows with w:", ratio[1000] > ratio[10])
print(f"ratio at w=10: {ratio[10]:.0f}, at w=1000: {ratio[1000]:.0f}")
```

```text
# output varies
window time grows with w: True
ratio at w=10: 5, at w=1000: 51
```

The window version does `w` additions for each output value. The cumulative-sum version does two, whatever the size of `w`. The ratio therefore grows in proportion to `w`, and the numbers above are of that order: 5 at `w = 10` and 51 at `w = 1000`.

## 2. [break]

`np.vectorize` finds the output type by calling the function on the first element. The first call returns the integer 0, so the output type is `int`, and the value 2.7 is cut to 2. NumPy gives no warning.

```python
import numpy as np

f = lambda v: 0 if v < 1 else v
broken = np.vectorize(f)(np.array([0.5, 2.7]))
fixed = np.vectorize(f, otypes=[float])(np.array([0.5, 2.7]))
print("broken:", broken)
print("fixed: ", fixed)
assert broken.tolist() == [0, 2]
assert fixed.tolist() == [0.0, 2.7]
```

```text
broken: [0 2]
fixed:  [0.  2.7]
```

The repair is `otypes=[float]`. This is a second reason, after speed, to prefer `np.where` over `np.vectorize`: `np.where(v < 1, 0.0, v)` has no output type to guess.

## 3. [judge]

**Position.** Not yet. First measure the run time on the real data.

**What a good answer weighs.** The loop ran at 3.6 million steps a second. A series of one million values takes 0.3 seconds. A series of 100,000 takes 0.03 seconds. If the job runs once an hour, this is not a problem. Numba adds a dependency, a compile step at startup and a second place for bugs.

If a request has 10,000 series of 100,000 values each, the same arithmetic gives 5 minutes. Then the speed matters. The size of the real data and the time budget decide. The chapter measured only the speed of the loop.

**Strongest objection.** A library routine for linear filters applies this recurrence in compiled code, with no new compiler. That is a better first step than Numba. This book did not measure it. A good answer says so and measures it before the choice.

**What overturns the position.** A profile of the real job can show the loop above the time budget. A measurement can then show that the library routine does not meet the budget either. Then Numba is the next step.
